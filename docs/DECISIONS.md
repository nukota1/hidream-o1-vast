# Decisions

最終更新: 2026-07-31 (JST)

## D-001 Flask + SSEによる生成処理

- 状態: 採用
- 決定: `POST /api/generate/start` でジョブを開始し、SSEで準備・進捗・完了を通知する。
- 理由: 既存Flaskアプリを活かしながら、長時間のモデル準備や生成状況をUIへ返せるため。
- 補足: GPU処理はロックで直列化し、モデル競合を防ぐ。

## D-002 Cloudflare Workerを公開ゲートウェイにする

- 状態: 採用
- 決定: ブラウザは固定のWorker URLへ接続し、Workerが認証、保存、Vast.aiへのプロキシを担当する。
- 理由: Vast.aiのURLがインスタンスごとに変わり、秘密情報をブラウザへ渡せないため。

## D-003 画像はR2、メタデータはD1へ保存する

- 状態: 採用
- 決定: PNGをR2へ、履歴・プロンプト・フォルダ・所有者情報をD1へ保存する。
- 理由: 大容量バイナリと検索可能な構造化データを適切に分離するため。

## D-004 推論モデルをDockerイメージに含めない

- 状態: 採用
- 決定: アプリだけをイメージへ含め、依存とモデルはVast.aiインスタンス起動後に取得して `/models` へ置く。
- 理由: 巨大なイメージレイヤーによるpull停止や起動遅延を避けるため。

## D-005 大型モデルを同時常駐させない

- 状態: 採用
- 決定: 画像生成、プロンプト最適化、画像編集の用途切り替え時に不要モデルをアンロードする。
- 理由: 32GB級GPUのVRAM不足を避けるため。

## D-006 立ち絵保持とイベントCG再生成を別モードにする

- 状態: D-013により標準フローとしては廃止
- 決定:
  - 背景変更の既定は立ち絵保持方式とし、`isnet-anime` で人物を抽出する。
  - 背景は保存済み背景マスクを使い、Waifu-Inpaint-XLで元画像の背景領域へ直接inpaintする。
  - diffusionとVAE処理後、マスク外の人物画素を元画像から復元し、人物本体の変化と透過を防ぐ。
  - ポーズ・カメラ・構図を変える場合だけintegratedでイベントCG全体を再生成する。
  - 立ち絵保持方式の指示にポーズ・表情・衣装変更が混在した場合は、変更を黙って無視せずイベントCG再生成へ案内する。
  - 人物マスクを抽出できない場合、人物を守るため全面編集へフォールバックしない。
- 理由: キャラクタープロンプトへの追従性と、生成済み立ち絵の背景変更容易性を優先しながら、別生成背景の単純合成で発生する接地感・遠近感・光の不一致を減らすため。
- トレードオフ: 人物ピクセルを保持する方式ではポーズ変更、人物前面を横切る前景物、人物内部への強い環境光は生成できない。実画像で輪郭マスク残りと人物透過を解消できなかったため、自動フローから外した。

## D-007 ローカルとVast.aiで当面異なる生成モデルを使用する

- 状態: D-017により廃止
- 決定: ローカルはAnimagine XL 4.0、Vast.aiはJANKU v7.77を既定とする。
- 理由: 現時点のローカル再現性とVast.aiでの生成実績を優先するため。
- 再検討条件: 実画像評価と運用コストを踏まえ、モデル統一の必要性が明確になった時点。

## D-008 DockerとGitHub Actionsを自動化の基盤にする

- 状態: 採用
- 決定: ローカルの主要なビルド・テストはDockerを優先し、コンテナ公開はGitHub Actionsを使用する。追加ツールは具体的な必要性が生じた時点で導入する。
- 理由: 現行環境でDocker Desktopが利用可能であり、ホスト環境への不要な依存追加を抑えつつ再現性を確保できるため。
- 補足: ローカルはモデルを `janku-models-local`、Python/CUDA依存を `janku-python-local` に永続化する。任意エディタの取得失敗は標準生成の起動を止めない。PRではコンテナをbuildだけ行い、`main`へのpush時だけGHCRとDocker Hubへ公開する。

## D-009 アニメ人物抽出と推論ライブラリを安定版へ固定する

- 状態: 採用
- 決定:
  - 人物抽出は `rembg[cpu]==2.0.69` の `isnet-anime` を使用し、モデルを `/models/rembg` へ永続化する。
  - `transformers==5.14.1` と `diffusers==0.39.0` を固定し、起動時にバージョンとCLIP互換性を確認する。
  - Qwen3.5-9Bは標準PyTorch経路を既定とし、`PROMPT_REFINER_USE_KERNELS=0` にする。
- 理由: 色ベースの背景抽出では白髪・白衣装を背景と誤認するため。開発版Transformersでは現行PyTorchにないAPIを要求してCLIP読み込みが失敗したため、動作確認済みの安定版を固定する。
- 補足: 公開済みのQwen activation kernelは現行Torch 2.7.1より新しいstable ABIを要求する。`kernels`を有効にすると日本語最適化が失敗し、未翻訳の日本語がCLIP長制限で落ちるため、互換版が確認できるまで無効にする。
- トレードオフ: `isnet-anime` でも半透明素材、極細の毛先、複数人物は誤差があり得るため、手動マスクと評価セットは引き続き必要。

## D-010 アプリ生成の立ち絵はクロマ背景と保存済みマスクを正本にする

- 状態: D-013により廃止
- 決定:
  - キャラクター生成では内部的に緑の単色背景を要求し、生成後は透明RGBA PNGへ変換する。
  - `isnet-anime`の人物判定と画面端から確認した緑クロマキーを併用し、髪の隙間や人物に隣接した元背景を背景マスクへ含める。
  - `isnet-anime`の信頼度は物理的な透明度として扱わず、判定済みの人物内部は完全不透明にする。
  - アンチエイリアス輪郭の1px範囲だけをソフトアルファとして保存し、クロマ色でない閉じた誤検出穴は人物として回復する。
  - クロマ背景と混色した境界色はアルファと背景色から人物色を逆算し、不透明な緑反射はデスピルする。
  - 生成した背景マスクを透明人物レイヤーとともにUIへ返し、背景合成時に再抽出せず同じマスクを再利用する。
  - 保存済みマスクがない透明PNGは自身のアルファを背景マスクとして使用する。
  - 外部画像は画面端が緑と確認できた場合だけクロマキーを使い、それ以外は`isnet-anime`によるセマンティック抽出を使う。
- 理由: 白背景と色距離だけでは白髪・白衣装を失い、セマンティック抽出だけでは髪の間の閉じた背景を人物と誤認することがある。一方、セマンティック信頼度を画像全体のアルファへ直接使うと、固体の髪・肌・衣装まで半透明になる。内部の二値判定、輪郭限定ソフトアルファ、クロマ色の確認、色の逆算を組み合わせることで、人物内部を不透明に保ちながら境界だけを自然に合成できる。
- トレードオフ: 半透明素材、極細の毛先、髪の隙間、背景との混色境界で二値／ソフトマスクの調整が競合した。コードは過去資産と手動修正の互換用に残すが、通常UIから自動実行しない。

## D-011 人物定義とシーン指示を分離した二段階生成を標準にする

- 状態: 人物・シーン分離だけ継続し、二段階inpaintはD-013により廃止
- 決定:
  - キャラクター生成画面で、人物の固定要素・表情・ポーズと、背景・シーンを別入力にする。
  - 第一段階は人物入力だけをモデルへ渡し、クロマ背景上の人物と再利用可能な背景マスクを作る。
  - 背景・シーン入力がある場合は、第一段階完了後に同じ操作内で背景inpaintを自動実行する。
  - 人物の重要タグは最適化後プロンプトの前方へ置き、背景語との競合を避ける。
- 理由: 人物と背景を同じ未整理プロンプトで扱うと人物要素が埋もれるため、入力と最適化は分離する。ただし描画は分離せず、人物タグを前方へ置いた一回の全画面生成に変更する。

## D-012 LoRA学習と少数参照による即時生成を別機能にする

- 状態: 採用・参照生成まで実装
- 決定:
  - ギャラリー画像を起点に、ユーザー別のSDXL LoRA学習ジョブを実装する。
  - 一枚学習は試験用途として許可するが、同一人物で角度・表情・ポーズ・照明が異なる10枚以上を推奨する。
  - 学習済みLoRAのトリガーワードを生成プロンプト前方へ自動挿入し、適用強度とともに資産メタデータへ記録する。
  - 一枚の参照画像を学習なしで反映するSDXL IP-Adapter Plusを実装し、LoRAと同時使用できるようにする。
- 理由: LoRAは反復利用に向く学習済み資産であり、少数画像を即時参照する編集モデルとは品質、待ち時間、必要画像数、再利用方法が異なるため。両者を同じ機能として扱うと、一枚学習で高い再現性が得られるという誤った期待につながる。
- トレードオフ: IP-Adapterを強くすると元構図や背景まで引きずり、弱くすると顔や衣装の維持が下がる。LoRA学習画像が少ない場合は過学習や背景・衣装の混入も起こり得るため、両強度を独立調整する。

## D-013 輪郭マスクを標準から外し、LoRA・参照画像による全画面再生成を標準にする

- 状態: 採用
- 決定:
  - シーン込みの新規生成は、人物入力とシーン入力を別々にQwenで最適化し、人物タグを先頭に置いた一回のSDXL全画面生成とする。
  - 背景、表情、ポーズ、カメラを変更するときは、元画像をSDXL IP-Adapter Plusへ渡し、Character LoRA、人物定義、変更指示を同時に使って一枚絵を再生成する。
  - 参照強度とLoRA強度は独立してユーザーが調整できる。
  - ギャラリー画像から人物定義、LoRA、画像を引き継いで一貫再生成画面を開けるようにする。
  - 自動人物抽出、クロマキー、背景輪郭マスク、人物画素復元は標準UIから使用しない。
  - Waifu-Inpaint-XLは、ユーザーが明示的に用意したマスクによる局所修正だけに残す。
- 理由: 髪の隙間、半透明素材、極細の毛先、アンチエイリアス境界では、マスクを広げると人物が透け、狭めると背景縁が残る。LoRAで同一性を長期保持し、IP-Adapterで選択画像の外見を補強し、人物と背景を同じ生成工程で描く方が、ADV・ライトノベル用の別カット作成と背景変更に適する。
- トレードオフ: 元画像の人物ピクセルは固定されず、「同じキャラクターの別カット」として再生成される。厳密なポーズ制御は将来のOpenPose ControlNet、完全なピクセル固定は手動マスクまたはレイヤー資産で扱う。

## D-014 参照画像は外見補助に限定し、厳密なポーズ制御をOpenPoseへ分離する

- 状態: 採用
- 決定:
  - SDXL IP-Adapter Plusは `h94/IP-Adapter` の `sdxl_models/ip-adapter-plus_sdxl_vit-h.safetensors` と、1280次元の `models/image_encoder` を組み合わせる。
  - 参照画像は人物中心部へクロップし、既定参照強度を0.25とする。旧背景のシーンタグはnegative promptへ移す。
  - 参照なし生成へ戻る際はIP-Adapterをunloadし、参照用のパイプライン状態を通常生成へ残さない。
  - Character LoRAは長期的な人物同一性、IP-Adapterは現在のカットの外見補助、テキストは背景・表情・演出、OpenPose ControlNetは骨格と手の配置を担当する。
  - 顔元のVサインなど厳密なポーズを必要とする機能は、ポーズ参照画像またはテンプレートを入力するOpenPose ControlNetとして別タスクで実装する。
- 理由: 参照強度を上げるだけでは元背景と元ポーズも固定され、新しいシーンへの追従性が落ちる。一方、下げるだけでは人物の外見維持が弱くなる。参照の対象を人物中心へ絞り、役割ごとに条件を分離する方が調整可能性が高い。また、SDXLのテキストとIP-Adapterだけでは手指を含むポーズを毎回保証できない。
- トレードオフ: OpenPose実装までは厳密なポーズ指定が確率的になる。人物中心クロップでも元衣装や構図の影響は残り得るため、LoRA学習画像の多様性と参照強度の調整が必要。

## D-015 Character LoRAは画像別キャプションと学習混入制約を使用する

- 状態: 採用
- 決定:
  - 学習画像ごとにcaption sidecarまたは `captions.json` を使用し、衣装、背景、ポーズ、表情を明示する。
  - 人物固有の顔、髪、目、装飾はトリガーワード側へ学習させ、生成時は保存済み人物定義でも補強する。
  - 縦長画像は正方形へ中央切り抜きせず、面積を基準に64px単位のアスペクト比バケットへ変換する。
  - お団子、髪留め、傷、左右非対称衣装などを守るため、Character LoRAのランダム左右反転は既定で無効にする。
  - 推奨ステップは画像数×20、最小200、最大800とし、過学習を避ける。
  - 学習セット全体で固定された背景などはLoRAメタデータの `training_leakage_tags` へ記録し、現在の指示に含まれない限りnegative promptへ自動追加する。
- 理由: 30枚すべてが白背景・同一衣装の実データでは、単一captionと正方形中央cropが人物全身を失い、白枠や固定衣装をLoRAへ混入させた。画像別caption、縦長bucket、混入タグ抑制により、人物定義を維持しながら別衣装・海背景を生成できた。
- トレードオフ: 全画像が同一衣装・同一背景の場合、captionで分離してもトリガーワード単独の再現性には限界がある。最も良いLoRAには、同一人物の別衣装・別背景・別照明の採用画像を含める必要がある。

## D-016 Character LoRAは固定人物定義を持ち、画風とは分離する

- 状態: 採用
- 決定:
  - Character LoRAごとに、髪、瞳、顔、体格など変更しない特徴を `identity_prompt` として保存する。
  - LoRA選択時は固定人物定義を人物入力の前へ自動挿入し、CLIP上限では画風タグより優先する。
  - このキャラクターは、後頭部中央の小さなお団子、前髪側の白い猫型髪飾り、採用画像を基準とするRose Crimsonの瞳、小柄で幼い顔立ちを正しい仕様とする。captionでは `rose crimson eyes, deep reddish-pink irises` を基準表現とし、固定HEX値へ依存しない。
  - 99枚から61枚を選別したv3では800ステップまで比較用重みを保存し、体格と装飾位置のバランスが最も良い400ステップ版を既定として採用する。
  - Character LoRAは人物同一性を担当し、元画像の画風を固定する責務は持たせない。画風固定は基盤モデル選定または同一基盤モデル向けStyle LoRAとして分離する。
- 理由: 初回評価では誤って `amber eyes`、`side bun`、`blue hairclips` を指定し、さらに長い人物・画風タグが77トークンのCLIP上限で脱落していた。実データの監査では白い猫型髪飾りが全角度で一貫していた。短い固定定義とv3 400ステップ版では目色、顔年齢、髪型、体格が改善した一方、画風はAnimagine XL 4.0へ寄るため、他キャラクターと共有するStyle LoRAを分離する。瞳色の最終表現は後続の採用画像監査でRose Crimsonへ確定した。
- トレードオフ: 固定人物定義は生成の安定性を上げるが、人物属性を意図的に変更する用途では競合する。Style LoRAを分離するには、同じ画風で人物・背景が異なる追加データが望ましい。

## D-017 Animagine XL 4.0 Zeroへ統一し、CharacterとStyleのLoRAを分離する

- 状態: 採用
- 決定:
  - ローカルとVast.aiの既定基盤を `cagliostrolab/animagine-xl-4.0-zero`、profileを `sdxl-animagine-zero` へ統一する。
  - LoRAメタデータへ正確な基盤profileを保存し、旧Animagine Opt・JANKU用LoRAをZeroへロードしない。
  - Character LoRAは人物同一性、Style LoRAは線画・塗り・色設計を担当し、同時に独立強度で適用する。
  - Characterはrank 16、学習率 `1e-4`、左右反転なしを既定とする。Styleはrank 32、学習率 `5e-5`、左右反転ありを既定とする。
  - Animagineの学習時タグ順に合わせ、人数・主体、Characterトリガー、Styleトリガー、変更指示、シーン、品質の順で渡す。
  - 人物LoRAは固定人物定義に加えて固定除外条件を持ち、誤ったお団子位置や体格をnegative promptへ自動挿入できるようにする。
- 理由:
  - Optは一般生成向けの追加調整を含み、Character LoRAだけでは好みの画風を他キャラクターへ再利用できなかった。
  - Zeroは公式にLoRA・追加fine-tuning向け基盤として提供されている。
  - ローカルとVastで基盤が異なると同じLoRA重みを安全に共有できず、生成結果の比較も成立しない。
  - 実教師画像では正面・斜め向きのお団子が側頭部へ突出しており、学習量を増やすだけでは誤配置を強化するため、データ修正と除外条件の両方が必要。
- トレードオフ:
  - 旧v2・v3 LoRAはZeroと互換扱いにせず、再学習が必要になる。
  - Style LoRAには同じ画風で人物・背景・構図が異なる追加データが必要で、単一キャラクター画像だけでは学習を完了できない。
  - Zero単体の出力品質はStyle LoRA適用前の基準であり、希望画風の達成を保証しない。

## D-018 Zero用Character LoRAは修正版36枚を正本にする

- 状態: 採用
- 決定:
  - Zero用Character LoRAの教師画像は、`input/学習用テストデータ/金髪ショートヘアの少女_Zero再学習/` の採用5フォルダ、合計36枚を正本とする。
  - 内訳はターンアラウンド12、表情差分12、白背景の全身基準6、衣装・背景・ポーズ差分6とする。
  - 正面では後頭部のお団子を無理に見せない。横、背面、振り返りで後頭部中央の位置と形を学習させる。
  - `00_カタログ`、`99_要修正`、`非採用` は学習対象へ含めない。完全重複画像を複数回学習させない。
  - 猫型髪飾りだけを人物固定要素とし、衣装の猫柄、バッグの猫柄、背景の猫は画像別captionで可変要素として分離する。
  - Character LoRAでは左右反転を無効にし、人物固定要素、視点、表情、姿勢、衣装、背景を画像別captionへ記録する。
- 理由:
  - 旧v3の髪型教師画像には、正面・斜め向きでお団子が側頭部へ突出する誤りがあり、学習量を増やすだけでは誤配置が強化された。
  - 新しい36枚は正面、左右45度、左右真横、背面、後頭部接写、表情、全身比率、実背景での動作を分離しており、人物同一性とプロンプト追従性を同時に評価しやすい。
  - 正面から見えない後頭部のお団子を毎画像へ強制すると、正面生成でも側頭部に描く誤学習を招く。
- トレードオフ:
  - 36枚だけでは画風を他キャラクターへ共有できない。画風は別のStyle LoRA用データで学習する。
  - 入力フォルダはGit管理外であり、文書やコードをpushしても教師画像は共有されない。
  - 現在の学習スクリプトはdataset直下だけを読むため、サブフォルダ構成の正本からフラットな学習datasetを作成する工程が必要になる。

## D-019 明示された人物・動作・シーンをQwenの要約結果より優先する

- 状態: 採用
- 決定:
  - Qwenによる人物・シーン最適化は継続するが、ユーザーが明示した人数、主要動作、場所、時間帯は短い英語タグとして別に保持する。
  - 最終promptでは `1girl, solo`、Character LoRA固定属性、今回の動作、シーン固有タグ、画風・品質の順で優先する。
  - Qwenが固有シーンを `outdoors` などの一般語へ縮約した場合も、海、駅、田んぼ道、夕方などの明示タグを再挿入する。
  - シーン込みの全身生成では縦長キャンバスと単一構図を優先し、人物複製、分割画面、参照シートをnegative promptで抑制する。
- 理由: 長い固定人物定義と画風語をそのまま結合すると、SDXLのCLIP上限でユーザーが今回指定した動作・背景が後方から脱落し、複数人物や単色背景へ逸脱したため。
- トレードオフ: 小さな装飾や複雑な手指はpromptに残っても毎回の視覚再現を保証できない。必要に応じてCharacter LoRA、追加学習、OpenPoseなど別の条件制御を併用する。

## D-020 複数候補はSeedだけを変えてGPUで直列生成する

- 状態: 採用
- 決定:
  - 1回の操作で指定できる生成枚数は1〜8枚とする。
  - 人物・シーンの最適化、LoRA設定、画風、サイズ、Steps、CFG、Sampler、Clip Skipはバッチ内で共通にする。
  - 1枚目はユーザー指定Seedを維持し、2枚目以降は重複しないランダムSeedを割り当てる。
  - GPU生成は並列化せず1枚ずつ実行し、完成画像をSSEで逐次返す。
  - 複数結果はSeed付き一覧として表示し、ユーザーが選択した1枚を保存、R2保存、一貫再生成の対象にする。
  - 画風強度はブラウザへ保存し、生成時メタデータにも記録して履歴参照時に復元する。
- 理由: 同一Seedでは同じ画像が再生成され、promptや画風までランダム化すると候補間の比較が難しくなる。Seedだけを変えると、画風と構図意図を維持しながら確率的な差分を得られる。直列実行は単一GPUのVRAM競合を避け、既存の生成ロックとも整合する。
- トレードオフ: 指定枚数に比例して待ち時間が増える。最大8枚に制限し、各画像の完了を進捗と結果一覧へ逐次反映する。

## D-021 Vast.aiの標準環境は現在使用中のモデルだけを準備する

- 状態: 採用
- 決定:
  - Vast.aiの起動時prefetchはAnimagine XL 4.0 Zero、SDXL IP-Adapter Plusとimage encoder、Qwen3.5-9Bに限定する。
  - JANKU、Waifu-Inpaint-XL、anime segmentation、FLUX.1-Kontext-dev、Qwen-Image-Edit、HiDream-O1-Imageは標準テンプレートへ設定しない。
  - HiDreamのソースと追加Python依存は `HIDREAM_RUNTIME_SETUP_ON_START=1` の場合だけ準備し、既定は無効にする。
  - Worker経由でギャラリーをR2へ保存する構成では、Cloudflare APIトークンと汎用 `R2_*` 認証をVastへ渡さない。LoRA永続化だけはD-022の専用 `LORA_R2_*` 認証を使用する。
  - Character・Style LoRAはユーザー資産として公開イメージへ埋め込まず、`/models/loras` をローカルキャッシュとして扱う。
- 理由: 32GB級GPU・120GB diskのVast.aiインスタンスで、使用しない大容量モデル、不要な依存、過剰な秘密情報を取得・保持せず、初回起動時間とディスク消費を抑えるため。
- トレードオフ: 未設定の任意エディタはそのまま利用できない。後から有効化する場合は、モデルごとに環境変数、アクセス条件、追加ディスク、互換依存を再確認する必要がある。

## D-022 ユーザー別LoRAはR2を正本、Vast.aiを検証済みキャッシュにする

- 状態: 採用
- 決定:
  - 学習済みLoRAのメタデータ、推論重み、学習設定はCloudflare R2を正本とし、Vast.aiの `LORA_ROOT` は交換可能なローカルキャッシュとする。
  - Cloudflare Accessの利用者IDはR2キーへ直接含めず、既存の `owner_storage_key()` と同じSHA-256由来のowner keyへ変換する。
  - Character、Style、および将来のPose・Background LoRAは同じ保存形式を使い、カテゴリと基盤モデルprofileをメタデータで判定する。
  - 学習完了後は成果物を先にアップロードし、全ファイルのサイズとSHA-256を持つ `metadata.json` を最後に置いて公開完了マーカーとする。
  - 推論に不要な中間checkpointは既定で保存せず、再公開時は新しいメタデータから参照されなくなった同一モデル配下の成果物を削除する。
  - LoRA一覧または生成要求時に、その利用者のR2プレフィックスだけを遅延同期する。復元時はサイズとSHA-256が一致したファイルだけをatomic renameし、破損した重みは登録しない。
  - 教師画像とcaptionは既定ではR2へ保存せず、保存期間、削除、プライバシー方針を定めたサービスだけが `LORA_R2_INCLUDE_TRAINING_DATA=1` で明示的に有効化する。
  - ギャラリーのR2 bindingとは権限を分離し、Vast.aiには `ai-model-cache` へ限定したObject Read & WriteのS3認証を `LORA_R2_*` として設定する。
- 理由: Vast.aiのインスタンスやディスクを交換してもユーザーの学習成果を失わず、複数ユーザーのCharacter・Style資産を相互に露出させずに同じアプリで扱うため。Dockerイメージへユーザー資産を入れないことで、公開イメージと私有データの境界も維持できる。
- トレードオフ: 一覧の初回表示ではR2 listingと必要な重みのダウンロード待ちが発生する。中間checkpointを既定で保存しないため、checkpoint単位のロールバックが必要な運用では明示的な保存設定が必要になる。複数Vast.aiインスタンスから同一モデルを同時学習する排他制御、削除API、保存期間管理は別途必要になる。
